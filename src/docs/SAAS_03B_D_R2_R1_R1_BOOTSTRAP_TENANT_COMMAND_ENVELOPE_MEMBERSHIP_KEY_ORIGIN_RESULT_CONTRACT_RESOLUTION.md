## Exact command input and envelope

BootstrapTenant accepts this exact top-level command input:

```text
{
  commandId,
  correlationId,
  tenantId,
  tenant: { tenantType, displayName, shortName, country, locale, timezone },
  settings: {
    defaultLocale,
    registrationPolicy: {
      openRegistration,
      invitationOnly,
      institutionalEmailOnly,
      manualApprovalRequired
    },
    featureFlags,
    supportEmail,
    supportUrl
  },
  branding: {
    displayName,
    logoUrl,
    faviconUrl,
    colors: { primary, secondary, accent }
  },
  firstAdminUid,
  expectedAdminEmail,
  initialStatus: "active"
}
```

All fields shown are required. Optional fields are zero. Nullable values are
`settings.supportEmail`, `settings.supportUrl`, `branding.displayName`,
`branding.logoUrl`, and `branding.faviconUrl`. Unknown fields are rejected.
Actor, authority, role, capability, claims, timestamps, membershipId, audit IDs,
server metadata, SDK objects and arbitrary metadata are forbidden.

`commandId`, `correlationId`, `tenantId` and `firstAdminUid` are operator-supplied
opaque identifiers validated before paths. Tenant/config values and normalized
expectedAdminEmail are operator-supplied verification/business inputs. Actor,
authority, membershipId, uidKey, timestamps and audit IDs are server-derived.

The earlier payload list omitted correlationId because it described the
behavioral payload rather than the complete command input. CorrelationId is an
exact required **command-envelope/input field**, persisted as the independent
command/audit binding. It is not part of behavioral payload hashing.

## Canonical behavioral payload and hash

The exact behavioral object is:

```text
{
  tenantId,
  tenant,
  settings,
  branding,
  firstAdminUid,
  expectedAdminEmail: normalizedExpectedAdminEmail,
  initialStatus: "active"
}
```

The canonical hash includes commandType `BootstrapTenant` plus that complete
object. It excludes commandId, correlationId and generated membershipId.
ExpectedAdminEmail is included after normalization because changing the verified
target evidence changes command behavior; the raw spelling is never persisted.

## Membership identity and MembershipKey origin

MembershipId is generated by the trusted command boundary before entering the
transaction callback. It is an opaque independent identifier, never derived
from UID or uidKey and never accepted from input. It is persisted in the
Membership and MembershipKey only. It is excluded from behavioral hash and from
the public/persisted command result.

On an unknown transaction outcome, reread the command and Tenant aggregate. A
succeeded command identifies the Tenant result; the first-admin membership is
recovered internally through the canonical MembershipKey when continuation or
integrity proof needs it. Replay does not generate another membershipId.

The historical statement that membershipId must be stored in the command result
is superseded: it confused internal aggregate recovery evidence with the public
stable command result. The current universal seven-field result is authoritative.

For first-admin bootstrap, both Membership and MembershipKey contain required,
nullable `originRequestId: null`. Null means the Membership originated from a
privileged bootstrap rather than RegistrationRequest. No command/request ID is
substituted.

## Exact result

The universal result remains exactly seven fields:

```text
{
  commandId,
  correlationId,
  operation: "BootstrapTenant",
  resourceType: "tenant",
  resourceId: tenantId,
  status: "succeeded",
  replayed
}
```

`replayed` is false for the committing execution and true for an exact replay.
The principal resource is the Tenant aggregate, not its first Membership. No
membershipId, email, config, Identity, claims or PII is returned.

## Tenant-admin Authority State initial tuple

The exact initial unversioned document is:

```text
{
  tenantId,
  activeCount: 1,
  revision: 1,
  lastCommandId: commandId,
  updatedAt: serverTimestamp
}
```

All fields are required and non-null. Unknown fields are rejected. Revision is
the count of committed authority-state mutations, so bootstrap creation is
revision 1. LastCommandId is coordination/history metadata for the latest
committed authority-state mutation; it is not ownership. Each later committed
count mutation increments revision once, sets its command ID and server-owned
updatedAt. Read-only validation/replay changes none of them.

## Exact audit contract

Bootstrap writes two Critical events in the same aggregate transaction. Both
use the same operation because they are two projections of one business event:

```text
operation = "BootstrapTenant.create"
level = "critical"
resourceType = "tenant"
resourceId = tenantId
result = "succeeded"
```

One event uses `tenants/{tenantId}/auditEvents/{auditId}` for Tenant history;
one uses `platformAuditEvents/{auditId}` for platform-authority oversight. Their
audit IDs are distinct, deterministic and precomputed outside the callback.
Both link the same commandId and correlationId.

Exact summaries:

```text
beforeSummary = { tenantExists: false }
afterSummary = {
  tenantStatus: "active",
  firstAdminStatus: "approved",
  tenantAdminActiveCount: 1
}
```

Exact metadata allowlist:

```text
{ stage: "completed", tenantType }
```

No other metadata is allowed. In particular, audit excludes email,
firstAdminUid, membershipId, uidKey, raw payload/settings/branding, Identity,
claims, credentials, approval artifacts, secrets, snapshots and stack traces.

## Command lifecycle and atomicity

BootstrapTenant is Firestore-only and has no external-effect recovery checkpoint.
A new command is not persisted as an orphan `pending/not_started` record. The
single transaction validates all preconditions and commits the complete
aggregate plus Command directly as `succeeded/completed`.

- pre-commit rejection or aborted transaction: command absent, zero writes;
- confirmed success: command `succeeded/completed` with seven-field result;
- unknown commit outcome: point-reread Command, then replay or safely retry;
- no `prepared` or `recovery_required` state is used by BootstrapTenant.

The package stage authorization must therefore allow BootstrapTenant only at
`completed` for its persisted successful command. Generic v2 validation still
recognizes not_started/prepared combinations for other command families; they
are not valid persisted BootstrapTenant checkpoints.

The atomic write set is Tenant, Settings, Branding, first-admin Membership,
MembershipKey, tenant-admin Authority State, Command, tenant audit and platform
audit. Every read occurs before every write. No Auth/network/randomness or
authoritative process-clock value occurs inside the callback.

## Replay, conflict and collision matrix

| Condition | Decision/effects |
|---|---|
| same commandId, same behavioral hash/correlation, succeeded | replay seven-field result with `replayed=true`; zero writes |
| same commandId, different behavioral hash | `CONFLICT`; zero writes |
| same commandId, different correlationId | `CONFLICT`; zero writes |
| different commandId, Tenant exists | `ALREADY_EXISTS`; zero writes |
| different commandId, independently existing Membership | `ALREADY_EXISTS`; zero writes |
| canonical key exists and points to that independently existing Membership | `ALREADY_EXISTS`; zero writes |
| key points to foreign/mismatched Membership or is malformed | `CONTRACT_VIOLATION`; zero writes |
| competing commands for same Tenant | exactly one commit; loser rereads and returns `ALREADY_EXISTS` (or `CONFLICT` only when bounded transaction contention prevents the authoritative reread); loser zero writes |
| transaction callback retry | deterministic IDs/data; one effective aggregate/audit commit |
| unknown commit result | reread Command; exact succeeded binding replays, absent command permits safe retry, malformed/incompatible command fails closed |

Invalid input/identifiers, invalid Platform Authority/capability, invalid target
Auth/Identity, malformed persistence, collisions and command conflicts all have
zero Command, Tenant, config, Membership, key, Authority State and audit writes.

Different Tenants may use the same firstAdminUid because Membership authority
and keys are tenant-local. The same canonical uidKey appears under different
Tenant parents without collision.
