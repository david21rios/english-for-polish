# SaaS-03B-C-R3-R2 — Platform Authority Transition Ownership Contract Resolution

## Status and scope

`SaaS-03B-C-R3-R2` is complete pending human review and push. It resumes the
ownership materialization after published `SaaS-03B-C-R3` and `R3-R1`; it does
not reopen their decisions. Its scope is the portable timestamp validator,
Platform Authority schema v1, transition ownership, generated declarations,
SemVer/artifact cutover, and compatibility validation. Transaction Store and
all business commands remain unimplemented.

## Portable timestamp

The package now owns pure, non-throwing `validatePersistedTimestamp`. It accepts
only a canonical UTC ISO-8601 string with millisecond precision
(`YYYY-MM-DDTHH:mm:ss.sssZ`) whose `Date` round trip is byte-identical. It
rejects null, undefined, non-strings, Date/number/object/array/Timestamp-like
values, empty/whitespace strings, offsets, missing or excess fractional
precision, impossible dates and other noncanonical representations.

The logical representation is the canonical string. Firestore native
`Timestamp` remains the physical adapter representation and `serverTimestamp()`
the write transform. Neither Firebase nor nullability is part of the primitive;
field contracts own nullability.

## Schema versions and compatibility

- `PLATFORM_AUTHORITY_SCHEMA_VERSION = 1`.
- `PLATFORM_AUTHORITY_REGISTRY_SCHEMA_VERSION = 1`.
- Deprecated `AUTHORITY_SCHEMA_VERSION` remains an identity alias of the
  Registry version for compatibility and is not used by new code.
- Missing, null, legacy unversioned, non-integer, unknown and future Authority
  schema versions fail closed. No compatibility reader or automatic migration
  exists because repository evidence identifies no deployed writer or concrete
  production Authority data from this backend.
- Registry retains its existing six-field shape and does not acquire an owner.

## Platform Authority schema v1

The exact 14 fields are, in order:

```text
schemaVersion
transitionCommandId
uid
authority
status
createdAt
createdBy
updatedAt
updatedBy
activatedAt
revokedAt
revokedBy
bootstrapCommandId
lastClaimSyncAt
```

All fields are required as keys and unknown fields are rejected.
`schemaVersion` is literal 1; `uid`, `createdBy`, and `updatedBy` are valid
document identifiers; `authority` is literal `platform_admin`.
`createdAt`/`updatedAt` are non-null canonical timestamps.
`activatedAt`/`revokedAt`/`lastClaimSyncAt` are canonical timestamps or null.
`revokedBy` and `bootstrapCommandId` are valid identifiers or null.
`transitionCommandId` is a valid identifier or null and is the sole local
primitive identifying the privileged command owning a non-stable transition.

The package-owned `validatePlatformAuthority` uses the established frozen
`ValidationResult` style, validates every result explicitly, and returns a
single sanitized `INVALID_ARGUMENT` issue for an invalid persisted shape.

## Status-owner matrix

| Status | `transitionCommandId` |
| --- | --- |
| `provisioning` | non-null valid ID |
| `active` | null |
| `revoking` | non-null valid ID |
| `revoked` | null |
| `recovery_required` | non-null valid ID |

Same-owner resume is conceptually permitted. A different owner conflicts;
generic takeover is prohibited. Clearing the owner while entering `active` or
`revoked` must be atomic in the future Store. Those cross-document checks,
registry counts/revisions, command and audit coordination, claim state and
transaction retry behavior are deliberately deferred to the Platform Command
Transaction Store Boundary.

`bootstrapCommandId` remains bootstrap history and Registry `lastCommandId`
remains registry coordination/history; neither is an owner candidate.

## Characterization

- Bootstrap can represent two `provisioning` Authority records owned by the
  same bootstrap command, with `bootstrapCommandId` also retaining history.
- Recovery accepts `recovery_required` only with a non-null owner.
- Revoke admits `active/null → revoking/owner → recovery_required/owner →
  revoked/null` shapes without implementing persistence or the command.

## Risk and rollback

The fail-closed schema intentionally rejects legacy/unversioned records. The
known risk is attempting to read a record not produced under schema v1; current
repository evidence shows no deployed writer/data requiring migration. Rollback
is the two-commit revert/cutback to package/artifact 0.7.0 before any v1 writer
is deployed. Once persisted v1 records exist, rollback requires an explicit
compatibility decision and must not reinterpret them silently.
